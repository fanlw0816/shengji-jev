2026-09-29 补齐两处（Plan 6 实施时发现）：`session.last_message` 此前**没有任何地方渲染**
（记账异常、热键注册失败写了看不见），以及 `zone_to_seat` 缺省为空导致实时运行时
四个区全部归到"自己"。

`setAttribute(WA_TransparentForMouseEvents, ...)` 会把

### [Plan 6 按家推断实现记录](superpowers/plans/2026-09-29-per-seat-inference.md)

功能 B：回答"这张牌可能在谁手里"。三类约束（面值总数 / 各家容量 / 空门）下的
**上下界传播到不动点**，输出 `candidates`（可能持有）与 `certain`（必然持有）。

**执行状态：✅ 引擎已实现并验证（31 项测试）；UI 接线断言同样已实际执行通过。**

含设计文档 §10.1 的 B1–B4 四项验收、紧致度基线回归、矛盾检测，
以及实施中发现的 3 个缺陷（详见文末）：

| 缺陷 | 后果 |
|---|---|
| `KnownSet.for_declarer` 按面值断言 H∩D 互斥 | **两副牌下合法牌型被拒**（手上 1 张 ♠A、底牌埋另 1 张） |
| `zone_to_seat` 缺省为空 | 实时运行时四个区全部归到"自己"，记账直接算错 |
| `session.last_message` 无人渲染 | "记账异常 / 热键注册失败"写了却看不见 —— 失败不可见 |

文末记录了**验证环境**的完整诊断：实施期间 `import numpy` 因 CPU 编译基线
（x86-64-v2）不满足而失败，一度导致 16 个测试模块无法收集；
后经 `pyproject.toml` 锁 `numpy>=2,<2.4` 解决，**全量 412 项现已在本机原生通过**。

### [Plan 7 推荐出牌（设计稿）](superpowers/plans/2026-09-29-play-recommendation.md)

功能 D：在记牌与按家推断之上回答「这墩该出哪张」。**本文件只有设计，没有实现。**

**执行状态：⬜ 仅规划，未实现。** 设计文档 §1 原本把它列为非目标（「不做 D 出牌建议」），
2026-09-29 转为远期规划（§1 与 §14 已同步；「不做胜率提示」那条保留）。

要点：

- **它和前三块不是一个量级**：记牌 / 推断是**事实性**任务（有客观真值），
  推荐是**评价性**任务（没有唯一正确答案）—— 难点在**先定义好"什么算一条好建议"**
- **四条可验收的硬约束**：R1 合法性（可完全枚举，最强锚点）、R2 不劣性（残局穷举对照，
  唯一硬真值）、R3 保守拒绝（前提缺失必须拒绝建议）、R4 理由可复核（**禁止胜率百分比**）
- **分层**：7a 合法着法枚举 → 7b 启发式评估（含**角色敏感**：庄家保底 vs 闲家抢分策略相反）
  → 7c 可能世界搜索（用 Plan 6 的 `candidates` 采样，取**最坏情况最优**而非期望胜率）
  → 7d 热键按需呈现
- **验收三层**：L1 残局穷举对照（硬真值）/ L2 性质测试 + 反平凡断言 R-t1~R-t4 /
  L3 统计对照（明确标注为**趋势证据，非真值**）
- **6 项前置阻塞一项未解决**：手牌区识别未验证（推荐的**第一输入**）、甩牌合法性规则未定、
  跟牌规则未实测、副级三门是否互压未定、角色与目标分未接入、主牌与底牌 ROI 未标定
  —— 其中四项属 Phase 0 现场标定，即 **Plan 7 排在所有现场标定之后**
- **风险差异**：出牌建议比纯记牌更接近"代打"，故**不做任何自动操作**（不点牌、不代打）

### 牌局引擎核心（Plan 4a / 4b，无独立计划文档）

主牌次序与墩赢家判定已实现于 `src/shengji/engine/`，见设计文档 §7.3 与 §7.6。

| 模块 | 内容 |
|---|---|
| `engine/trump.py` | 主牌判定、牌力次序（**含正级/副级**）、比较、排序、主牌集合枚举 |
| `engine/trick.py` | 结构判定（单张/对子/拖拉机/甩牌）、墩赢家、分牌点数 |
| `engine/accounting.py` | 变体规则表、已知集合、未见牌池、未知底牌堆、不变式 I1/I2 |
| `engine/inference.py` | 按家推断（功能 B）：空门追踪 + 上下界传播 |

**已实现并验证**：单张、对子、拖拉机结构；主牌压副牌；强弱相等先出者赢；
非领出花色且非主牌者不能赢；分牌点数统计；记账模型的三类重复扣减缺陷全部有回归测试。

**明确未实现**：**甩牌（一次出多张杂牌）的赢家判定**。
完整规则需判断甩牌合法性（是否均为该花色最大）与各家跟牌的结构匹配，
规则复杂且地区差异大。当前实现保守地让领出方赢，但返回 `confident=False`，
由上层走人工确认流程 —— 与设计文档 §9.1「宁可让你点一下，也不静默算错」一致。

**未验证变体拒绝启动**：`(6, 3)` 的手牌数/底牌张数标注为 `UNVERIFIED`，
`get_variant_rule` 遇到它会抛错，而不是采用猜测值。

**待实测确认**（设计文档 §7.6.3）：副级三门之间是否可互相比较。
默认实现为「同级、不可互压」，该差异直接影响墩赢家与分牌归属。

### 记账模型修正的三个缺陷

`engine/accounting.py` 对应设计评审抓出的最严重问题，每个缺陷都有回归测试：

| 缺陷 | 后果 | 修正 | 回归测试 |
|---|---|---|---|
| 快照时点混用 | 扣底后的 H 与扣底前的 P 有交集（`P − D`），重复扣减 | 统一采用扣底后 `(H, D)`；构造期按**牌堆构成**判，运行期由 I1 兜底 | `test_mixed_snapshots_surface_at_play_time` |
| `played ∩ known` | 自己打出的牌已在 known 中，再扣会让未见池变负 | 只对「来自 known 之外」的牌扣减 | `test_own_play_does_not_decrement_unseen` |
| 底牌不属于任何一家 | 计数约束把底牌派给某家，破坏 `certain ⊆ ground_truth` | 显式保留容量受限未知堆 `bottom_unknown` | `test_bottom_unknown_is_reserved_so_invariants_hold` |

> **后续修正（2026-09-29）**：初版对「快照混用」用「按面值断言 H ∩ D == ∅」来拦截，
> 但两副牌同面值有 2 张（庄家手上 1 张 ♠A、底牌埋另 1 张是合法牌型），
> 该断言会**拒绝合法输入**。现改为按牌堆构成判定，混用改由运行时不变式 I1 捕获
> —— 代价是构造期不再总能拦下，详见
> [Plan 6 文档](superpowers/plans/2026-09-29-per-seat-inference.md) 的缺陷 ①。

后续计划的范围见根 README 的状态表：**Plan 5 遗留的交互式纠正面板**
（见 [Plan 5 文档](superpowers/plans/2026-09-28-ui.md)），以及
**Plan 7 推荐出牌**（[设计稿](superpowers/plans/2026-09-29-play-recommendation.md)，仅规划未实现）。

## 实测证据（`spike/`）

设计中的每个常量都来自这些脚本的实测输出，改常量前请先重跑复核。

| 脚本 | 测什么 | 关键结论 |
|---|---|---|
| `bench_capture.py` | mss 与纯计算成本 | mss 整屏 17.7ms；absdiff 0.019ms |
| `bench_capture2.py` | dxcam 与模板匹配 | 模板匹配 0.145ms/次 |
| `bench_decisive2.py` | dxcam 增量语义 | 无变化时 `grab()` 返回 `None`，0.038ms |
| `bench_truth.py` | **交叉验证** | dxcam 46.7 FPS 与 mss 地面真值 46.3 Hz 吻合 → 不丢帧 |
| `analyze_screenshots*.py` | 四区真实布局 | 十字四宫格；1 张牌 56px、2 张 72px |
| `analyze_felt_threshold.py` | 桌面色能否定位牌桌 | **不能** —— 背景与桌面同色 |
| `analyze_card_blobs.py` | 牌尺寸块筛选 | 面积是区分牌块与同形 UI 元素的唯一特征 |
| `bench_this_machine.py` | **当前开发机复测**（KVM 虚拟机）：抓屏/热路径/帧率/模板匹配/牌几何 | 热路径 0.385 ms/帧（基准机 0.042）；新帧率 17.3 FPS（基准机 46.7）；牌几何与基准机**完全一致** |
| `bench_present_rate.py` | **帧率归因定案**：GDI BitBlt 成本 vs 区域大小 + 动画间隔扫描 | GDI 存在 **~59.5 ms 固定停顿**（16×16 与 1916×998 同价）→ 与显示刷新同步；dxcam 在 5/10 Hz 请求下 1:1 跟上 → **未丢帧，是虚拟显示只有约 16~22 Hz** |

**踩坑记录**：早期一次测量得出「dxcam 只有 12 FPS」，是**测量方法缺陷**
（用 `latest_frame_ticks` 计数）造成的假象。后经 mss 地面真值交叉验证推翻。
结论一律以交叉验证版本为准。

**第二次踩同一个坑（2026-09-29，当前机复测时）**，两处都属测量方法缺陷，已修：
① 用 mss 当"地面真值"测屏幕变化率，但 mss 在本机采一帧要 60 ms（= 16.6 Hz），
**真值被自己的采样率截断**，无法区分"屏幕就是 16 Hz"与"屏幕更快但我采不到"；
② 改用 GDI BitBlt 当高采样率真值，结果它**同样是 ~59.5 ms/次** —— 于是转向
「固定停顿 vs 像素相关」的成本-尺寸扫描，才把归因钉死。
另有一处：dxcam 段跑在主线程却没 pump Qt 事件，动画被冻住，测出 0 Hz。
**教训**：交叉验证前先量"验证手段自身的能力上限"，否则只是用一个慢尺子量另一个慢东西。
