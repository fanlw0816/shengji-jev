## 为什么这一层值得单独做

`accounting.py` 已经知道**还剩哪些牌**，但它不知道**在谁手里**。
人打升级时的读牌就是在这里发生的：不是算概率，而是排除 ——
"对家第一轮出红桃时垫了方片，那它就没有红桃了"。

所以本模块只做**逻辑排除与容量强制**，**明确不做概率推断**（设计文档 §7.4.2：
无客观验收标准，YAGNI）。

---

## 建模的三类约束

| 约束 | 来源 | 作用 |
|---|---|---|
| 面值总数 | 未见池计数 | 某面值剩余的张数必须在「能持有它的堆」之间分配完 |
| 堆容量 | 各家剩余持牌数 / 未知底牌容量 | 每个堆必须**恰好**填满自己的张数 |
| 空门（void） | 出牌历史 | 直接排除整组面值，实战中最强的信息来源 |

**堆**（pile）= 其他各家 + 一个未知底牌堆（庄家视角容量 0，非庄家 8）。
按**组**而不是按花色记空门：级牌属主牌组，所以"这家人打光了红桃"与
"这家人还有 ♥2"并不矛盾 —— 用 `group_of()`（`engine/trump.py`）统一判定。

## 算法：上下界传播到不动点

```
upper[p][f]  堆 p 至多持有几张 f      → candidates[p] = {f : upper ≥ 1}
lower[p][f]  堆 p 至少持有几张 f      → certain[p]    = {f : lower ≥ 1}

循环（有限步内收敛）：
  ① 面值级强制：某面值剩 c 张，若「除 p 之外的堆最多只能容纳 X 张」，
     则 lower[p][f] ≥ c − X；若全体上限之和 < c，则无解 → 报错
  ② 上界夹紧：upper[p][f] ≤ c − Σ_{q≠p} lower[q][f]（别人已"必然持有"的部分我不能有）
                upper[p][f] ≤ 剩余自由容量（这一步把容量耦合传下去）
  ③ 堆容量自洽：Σ lower ≤ 容量 ≤ Σ upper，违反即报错
  ④ 无变化则收敛
```

**为什么这样是可靠的**：每一条界都必须在**所有与已记录历史一致的牌局世界**里成立。
`lower` 只增、`upper` 只减，取值空间有限 ⇒ 单调 ⇒ 必然收敛（迭代上限只是保险，
真不收敛会明确抛错而不是给个半成品）。

**为什么偏宽是安全的**：未建模的约束（对子结构、连对可行性、甩牌合法性）只会让
`candidates` 偏宽，而**超集仍满足 B1**；偏窄才会破坏 soundness。
所以这里不追求"最优解"，只保证"可靠且不平凡"。

### 本模块能排除什么、不能排除什么（诚实边界）

排除性只来自两类事实：

1. **空门**：整组面值从该家 `candidates` 中消失
2. **容量为 0**：该家牌已打完 / 底牌容量为 0（庄家视角）

**不推导**的（宁可更保守，`certain` 更空）：

- 聚合约束，如"这家某花色至少还有 N 张"——只有逐面值的必然，没有"某组至少 N 张"
- 对子 / 连对的结构可行性（不知道人家有没有对，也不影响候选超集）
- 概率与期望

`certain` 因此可能比理论上更空 —— 而**更空是安全的**（`∅ ⊆ ground_truth` 恒真）。

## 空门从哪里来（`VoidTracker`）

判据是标准跟牌规则：**有该群的牌就必须跟，有多少跟多少**。
因此某家在领出组为 g 的一墩里，打出的 g 组牌**少于领出的张数** ⇒ 它对 g 组空门。
（"少于"同时覆盖了"一张都没出"与"领出对子只跟出一张"两种情形。）

两条**保守放弃**规则 —— 因为推错空门不是"变宽"，而是**破坏 soundness**：

1. 领出是甩牌 / 跨组杂牌时不推（跟牌规则地区差异大）
2. 该家本墩没有出牌记录时不推

⚠️ **未核实前提**：本推导依赖客户端强制「有该花色必须跟」。
若实测证伪，`candidates` 会**漏掉真值**（B1 直接失败），不是仅仅变宽 ——
这项与设计文档 §14 的现场标定一起实测确认。

## 验收（设计文档 §10.1，四条同时成立）

| # | 断言 | 防的是什么 | 本仓库对应测试 |
|---|---|---|---|
| B1 | `ground_truth[s] ⊆ candidates[s]` | soundness | `test_soundness_midgame` / `test_soundness_with_pair_leads` |
| B2 | `certain[s] ⊆ ground_truth[s]` | certain 的 soundness | 同上（`assert_soundness` 一并断言） |
| B3 | 可证在别家的牌不得出现在本家 `candidates` | **平凡全集解** | `test_constructed_void_excludes_whole_group` |
| B4 | 构造场景中存在 `certain[s] ≠ ∅` | **恒空集解** | `test_certain_is_nonempty_when_forced` |

B3/B4 用**手写牌型**而不是随机发牌：设计文档要的是"构造场景"，
随机发牌只能碰运气凑出空门。构造方式（`_construct_heart_void_scene`）：

```
自己手上 25 张红桃（牌堆共 26 张），下家与对家手上全是非红桃
  → 两家对红桃组空门（B3 可断言）
  → 剩下的 ♥A 只可能在上家手里（庄家视角底牌容量 0 ⇒ B4 可断言）
```

### 紧致度回归

记录构造场景与随机对局的 `candidate_total` 基线（112 / 113，无信息时 114），
**取值变化即报警**；另有 `test_tightness_grows_with_information`：
多逼死两张红桃，`candidates` 必须更小（防"紧致度与信息无关"的退化实现）。

> 诚实说明：这两个场景的绝对紧致幅度很小（112 vs 114），因为可用的硬信息本来就少。
> 基线机制的作用是**发现退化**，不是宣称"推断很强"。

### 矛盾检测

以下情形一律抛 `InferenceError`（继承 `AccountingError`，复用既有异常通道），
并在悬浮窗上显示，**绝不返回一个"看起来能用"的结果**：

| 情形 | 含义 |
|---|---|
| 某面值余牌数超过所有能持有它的堆的容量之和 | 识别重复 / 错认 |
| 某堆容量超过它可能持有的面值上限（填不满） | 空门推错 / 识别错 |
| 上下界自相矛盾（某堆至少需要 X 张、最多只能有 Y < X 张） | 同上 |

## 实施中发现并修正的缺陷（3 个）

### ① `KnownSet.for_declarer` 的「H ∩ D 不重叠」断言在两副牌下误报（真缺陷）

初版按**面值**断言手牌与底牌互斥。但两副牌每种面值有 2 张，**庄家手上 1 张 ♠A、
底牌埋另 1 张 ♠A 是完全合法的牌型** —— 实测发牌即命中，合法输入直接被拒。

- **修正**：改按**牌堆构成**判（同一面值合计不得超过牌堆张数），
  那才是识别重复（同一张被认两次）或快照混用的信号
- **代价（写进代码注释）**：快照混用不再总能在构造时拦下。若重叠面值恰好都是 2 张一副，
  各面值计数仍然合法，此时改由运行时不变式 I1 捕获：被重复计入已知的那几张，
  别人一打出就触发「未见池中已无此牌」。回归测试 `test_mixed_snapshots_surface_at_play_time`

### ② `zone_to_seat` 缺省为空 ⇒ 实时运行时四个区全部归到"自己"

`EventPipeline` 的 `zone_to_seat` 默认 `{}`，而 `CounterApp` 此前没有默认映射，
于是每个区都落到 `own_seat`：出牌全算自己打的，**记账直接算错**
（`seat_holds[自己]` 会一路扣到负数并报「只剩 N 张却打出 M 张」）。

- **修正**：加入可覆盖的默认值 `DEFAULT_ZONE_TO_SEAT`，取自设计文档 §11.2 的**实测布局**
  （`bottom`=自己 / `right`=下家 / `top`=对家 / `left`=上家）
- **边界**：这不是"隐式约定"——非 4 人局不使用它，映射为空时状态栏明说"未标定区→座位映射"，
  而不是悄悄算错（设计文档 §7.5）

### ③ 异常消息此前写了没人显示（静默失效）

`CounterApp` 一直往 `session.last_message` 写「记账异常：…」「热键注册失败：…」
「已强制重读 N 个区」，但视图模型与悬浮窗**都没有读它** ——
"失败要可见"在 UI 这一层是空的。

- **修正**：`OverlayView.message_text` + 悬浮窗上的一行标签

## 验证环境（重要 → 已修复）

### 原始症状

本机 `import numpy` 直接抛：

```
RuntimeError: NumPy was built with baseline optimizations:
(X86_V2) but your machine doesn't support: (X86_V2).
```

### 根本原因（2026-09-29 定位）

**不是本机"跑不了"，是依赖版本选高了。**

numpy 自 **2.4.0** 起把官方 wheel 的编译基线从 x86-64 抬到 **x86-64-v2**
（要求 SSE4.2 + POPCNT，见 numpy 2.4.0 release notes）。而本机是**虚拟机**：

| 项 | 值 |
|---|---|
| `Win32_ComputerSystem.Manufacturer` | `SANGFOR` |
| `Win32_ComputerSystem.Model` | `Standard PC (i440FX + PIIX, 1996)`（QEMU/KVM 默认机型） |
| `HypervisorPresent` | `True` |
| 暴露的 CPU 型号 | `Intel Core 2 Duo T7700 @ 2.40GHz`（2007 年 Merom；双核却报 4 逻辑核） |

实测指令集：SSE2 ✅ / SSE3 ✅ / SSE4.1 ❌ / SSE4.2 报 True 但 **POPCNT ❌** / AVX ❌
（SSE4.2=True 与 SSE4.1=False 自相矛盾 → 证实 CPUID 被虚拟化层伪装）。
不满足 x86-64-v2，因此 numpy ≥ 2.4 拒绝加载，`cv2` / `PySide6` 依赖链一并失败。

**环境变量绕不过**：`NPY_DISABLE_CPU_FEATURES` / `NPY_ENABLE_CPU_FEATURES` 实测均无效 ——
基线校验是编译期写进扩展二进制的，与运行时的 SIMD dispatch 开关是两回事。

### 修法

`pyproject.toml` 把 `numpy>=2.5.3` 改为 **`numpy>=2,<2.4`**（现解出 2.3.5）。
`opencv-python 5.0.0.93` 只要求 `numpy>=2`，兼容；numpy 2.3.x 仍以 x86-64 为基线。
迁到较新 CPU 的机器后可放宽回 `numpy>=2`。
