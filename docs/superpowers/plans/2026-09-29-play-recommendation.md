- **对应**：设计文档 §1「明确不做」中原本排除的 **D 出牌建议**，本次转为远期规划（§1 与 §14 已同步）。

## 1. 定位与边界

| 项 | 内容 |
|---|---|
| 输入 | 完整局面快照：自己手牌、当前墩与领出方、主牌、分数与目标分、各家 `candidates`/`certain`、各门空门 |
| 输出 | **2–3 个候选着法** + 每条一条**结构化理由**；前提不成立时输出「拒绝建议 + 拒绝原因」 |
| 触发 | **只在热键按下时**计算（拟定 `Ctrl+Alt+R`），不做实时自动更新 |
| 不做 | 不自动点牌 / 不代打；不显示胜率或概率数字；不做实时（逐帧）推荐 |

**与记牌、推断的根本区别**：前两者是**事实性**任务（这张牌在谁手里，有客观真值），
推荐是**评价性**任务（该出哪张，没有唯一正确答案）。所以本计划真正的难点不是搜索算法，
而是**先把「什么算一条好建议」定义到可验收**。这一点定不下来，写出来的推荐器就只能靠
「看起来合理」，与本项目「失败要可见」的约定直接冲突。

## 2. 「好建议」的四条硬约束

四条都必须是**可被独立复核的判断**，而不是主观感受：

| # | 约束 | 判据 | 能否离线验收 |
|---|---|---|---|
| **R1** | **合法性** | 建议的着法必须在规则允许集合内：有领出花色必须跟、跟不够才可垫/将吃；对子、拖拉机、甩牌的结构匹配 | ✅ 完全可枚举，最强 |
| **R2** | **不劣性** | 残局（各家剩余牌数少到可穷举）中，建议**不劣于**完美信息最优着法 | ✅ 唯一能拿到硬真值的场景 |
| **R3** | **保守拒绝** | 任一前提缺失（主牌未识别、自己手牌不完整、甩牌规则未定、推断报矛盾、`confident=False`）→ **必须拒绝给建议**，不得给一个"看起来能用"的 | ✅ 可构造触发用例 |
| **R4** | **理由可复核** | 每条理由都是可从 `UnseenPool` / `VoidTracker` / `inference` 查证的事实陈述（如"该门四家共剩 3 张，其中两家已空门"） | ✅ 逐条对账 |

> R4 直接**禁止**出现「胜率 62%」这类无法复核的数字。这是设计文档 §1 保留
> 「不做胜率提示」那条非目标的落地方式 —— 不是不给建议，是**不给不可验证的建议**。

## 3. 分层实现思路

四层由易到难，**每层可独立验收**，不要求一次做全。

### 7a 合法着法枚举 `legal_moves(hand, lead, trump, profile) -> LegalMoves`

> ✅ **已实施（2026-09-30）**，代码在 `src/shengji/engine/legal.py`，测试 `tests/test_engine_legal.py`（32 项）。
> **落点与本节原稿有一处刻意的偏离**：返回 `LegalMoves(moves, complete, notes)` 而不是裸的
> `list[Move]`。理由是「这个集合是不是完备的」本身就是调用方必须看见的信息 ——
> 7c 若在一个**不完备**的合法集合上搜索，算出的"最优解"是假的。详见 §10。

把「能出什么」和「该出什么」彻底分开 —— 这是整个计划的第一个动作，
因为 R1 是最强的验收锚点，先把它做好，后面所有评价都只在一个已知合法的集合里排序。

- `Move` 携带 `structure`（单张 / 对子 / 拖拉机 / 甩牌）与 `cards`
- 复用现有 `engine/trick.py` 的结构判定做**自洽校验**：枚举出的每一手都要能被它判为合法
- 与 `KnownSet` / 手牌对账：**绝不枚举手上不存在的牌**（识别错认会在这一步暴露）

### 7b 手牌评估（启发式，不搜索）

把人对升级的直觉编码成几个可解释的特征，产出**优先级 + 理由**：

- **控制力**：各门的大牌数（能否拿到出牌权）
- **长度**：各门张数 —— 拖拉机潜力
- **分牌保护**：手上 5 / 10 / K 的分布，决定"这墩让不让"
- **空门价值**：已有空门 = 后续可将吃
- **角色敏感**：庄家保底与闲家抢分**策略相反**，同一个局面两种角色的推荐可以完全不同
  （所以必须先接入角色与目标分，见 §6）

### 7c 可能世界搜索（可选，锦上添花）

用 Plan 6 的 `candidates` 采样出**与观测一致的可能牌局世界**，在每个世界里做完美信息求解
（残局 α-β，规模放大后退化为小规模 MCTS），再对多个世界取**最坏情况最优**。

**关键取舍：不做期望胜率，做最坏情况保证。** 理由：期望值需要假设对手的出牌分布，
而"对手是什么风格"我们没有可靠数据；而最坏情况只需要 `candidates` —— 那已是**已被证明的
可靠超集**（Plan 6 的 B1）。这与本项目「偏宽安全」的哲学一致：
**不为一种猜测下注**，也不让采样越出 `candidates` 半步。

> 这里的"概率"只存在于**搜索内部的随机性**，绝不出现在输出里 ——
> 输出永远是「哪条线索支持这个着法」的确定性理由。这是对设计文档里
> 「按家推断不做概率」原则的**兼容式延伸**，而不是推翻它。

### 7d 呈现

- 新增 `OverlayView.advice_text`，与现有 `inference_text` / `message_text` 同构
- 只在热键按下时计算并显示，避免逐帧搜索烧 CPU，也避免画面闪烁
- 前提不足时显示「拒绝建议：<原因>」，而不是留空（留空会被误读成"没算")
- 建议框**不得覆盖出牌区**（现有悬浮窗已有位置约束，沿用）

## 6. 阻塞项（**7b 起**必须解决；7a 已用参数化绕开）

> **修订（2026-09-30）**：本表原先写「当前一项都未解决」。核对后要分成两件事 ——
> **「规则取值未知」不等于「算法写不了」**。本项目已有现成模式（`get_variant_rule` +
> `UNVERIFIED` 拒绝启动），凡「算法可写、只是常量取值未知」的项都能先把框架做出来，
> 把未知常量留成**注入参数**。7a 就是这么落地的（见 §10）。
> 下面每一项都补了「卡在哪」这一列。

| 阻塞 | 卡在哪 | 为什么挡路 | 出处 |
|---|---|---|---|
| **甩牌合法性规则未定** | 规则取值 | 甩牌合法要求「所甩各张都是该门最大」，**依赖别家手牌，离线不可判定** | Plan 4a 未完成 + Phase 0 待实测 |
| **跟牌规则未实测** | 规则取值 | R1 的合法性判据直接建立在「有该花色必须跟、有多少跟多少」上 | Phase 0 待实测 |
| **副级三门是否互压未定** | 规则取值 | 直接影响 7b 的「控制力」 | 设计文档 §7.6.3 |
| **手牌区识别未验证** | 输入来源 | 推荐的第一输入就是「自己手上有什么牌」；手牌 25 张紧贴重叠、每张仅露约 13px，能否识别未验证 | README 已知限制 |
| 主牌指示区 / 底牌 ROI 未标定 | 输入来源 | 主牌识别错 → 全部着法评价都错 | Phase 0 待标定 |
| **角色与目标分未接入** | 尚未设计 | 没有目标函数就无所谓"最优"；庄家保底与闲家抢分策略相反 | 设计文档 §7.2 状态机 |

分法：

- **「规则取值」类（前三项）** —— 7a 已解决：取值进 `RuleProfile`，未知即 `UNVERIFIED`，
  `get_rule_profile()` 拒绝启动。Phase 0 实测结论出来后**只改常量、不动算法**。
- **「输入来源」类（两项）** —— **离线确实无解**，必须真机标定。它们挡的是 7d 的落地，
  不挡 7a/7b/7c 的开发（那三层都能用手写局面测）。
- **「尚未设计」类（一项）** —— 7b 的前置，可以在离线阶段先设计。

> 结论也随之修正：原先写「推荐出牌排在所有现场标定之后」。
> 更准确的说法是：**7a/7b/7c 均不依赖现场标定，只有 7d 的端到端落地依赖它**。

## 7. 验收方案（三层，从强到弱）

### L1 硬真值：残局穷举对照

构造每家 ≤ 6 张的残局（可穷举），用完美信息求解器算出精确最优，
断言 **建议不劣于最优**。这是整个计划唯一能拿到客观真值的场景，
也是评估函数是否跑偏的**唯一硬证据**。

### L2 性质测试（不需要真值）

- **合法性**：枚举集合 ⊆ 规则允许集合（R1）
- **拒绝触发**：任一前提缺失 → 必 `refused=True`，且 `refusal_reason` 指明缺哪一项（R3）
- **可解释性**：每条理由都能在 `inference` / `voids` / `pool` 里查到对应字段（R4）
- **反平凡断言**（对照 Plan 6 的 B3/B4 风格，防"看起来能用"）：

| # | 断言 | 防的是什么 |
|---|---|---|
| R-t1 | 不得出现「对任何局面都推荐同一手牌」 | **退化常量策略** |
| R-t2 | 不得出现「永远 `refused=True`」 | **恒拒绝**（等于没做） |
| R-t3 | 建议的着法必须 ∈ `legal_moves` | **非法建议** |
| R-t4 | 残局用例中存在「建议 ≠ 启发式首选项」的情形 | 搜索层被绕过（7c 存在性） |

### L3 统计对照（趋势证据，**非真值**）

在离线模拟器里跑 N 局：「建议器」VS「随机合法着法」VS「简单启发式」，
要求显著占优。

> ⚠️ 明确标注：这是**趋势证据**。本项目一切结论以实测为准，
> 统计对照只能说明"没坏到离谱"，不能当验收真值 —— 与
> [调研笔记](../../research/2026-09-28-prior-art-and-risks.md) 里
> 「结论一律以交叉验证版本为准」同一条纪律。

## 9. 为什么当初只规划、不实现（**已部分推翻，原文保留**）

> **修订（2026-09-30）**：本节是 2026-09-29 的判断，现被 §6 的修订与 §10 的实施记录
> 部分推翻 —— 「三个硬前置一个都没解决」里的前两个属**规则取值未知**，
> 并不妨碍先把枚举器写出来。原文保留，作为判断偏差的记录。

1. **三个硬前置一个都没解决**：手牌区识别未验证（推荐的第一输入）、甩牌规则未定（无法穷举合法着法）、
   跟牌规则未实测（合法性判据的地基）。现在写出来的推荐器**无法通过 L2 合法性验收**，
   更谈不上 L1 —— 只能靠"看起来合理"。
2. **与项目约定冲突**：本项目要求「实测优先于推断」「失败要可见」。
   一个没有客观真值的模块先写代码，等于先欠一笔债。
3. **正确的顺序**：先把 Phase 0 的标定做完（尤其是**手牌区**与**跟牌/甩牌规则**），
   让 7a 的地基可验证，再动 7b。本文件的作用是**先把验收标准定死**，
   这样等前置齐了可以直接开工，而不是到时候边写边想"怎么证明它是对的"。

## 11. 实施记录（2026-09-30 第二批）：§10 缺陷 1 已修

### 触发

§10 把「`structure_of` 不含级牌语义」记为**未修**，理由有两条：改它要传 `trump`、
波及三处；且规则本身待实测。第二条当时被当成「所以不能改」——
**这个推论是错的**：待实测的只是**取值**（级牌挖掉后前后是否接上），
而「跨组不能成连对」「级牌不与同门点数相邻」这两条**不需要任何实测**就能定，
它们直接由引擎自己的分组与层次模型（`group_of` + `card_strength`）推出。

于是重做一遍分类：把「规则取值未知」与「判定逻辑写错」分开 ——
前者参数化后离线照做，后者当时就该修。

### 实际错了几处（实证，非推断）

用 `structure_of` 直接跑 6 个手牌组合（打 10、主 ♠）确认：

| 情形 | 修前 | 修后 | 性质 |
|---|---|---|---|
| ♥10♥10 + ♥9♥9 | `TRACTOR` | `MIXED` | **跨组**：`♥10` 属主牌组、`♥9` 属 ♥ 组。更糟的是 `cards[0]` 是 ♥10，整手被当成**主牌**连对 |
| ♥J♥J + ♥10♥10 | `TRACTOR` | `MIXED` | 同上（顺序相反） |
| ♦J♦J + ♦10♦10 | `TRACTOR` | `MIXED` | 同上 |
| ♠10♠10 + ♠J♠J | `TRACTOR` | `MIXED` | 级牌自成一层 |
| ♠10♠10 + ♠9♠9 | `TRACTOR` | `MIXED` | 同上 |
| ♠J♠J + ♠9♠9 | `MIXED` | `TRACTOR` | 漏判（级牌挖掉后相邻） |

前三行是**修前完全没被注意到的**：原记录只写了「含级牌的连对」与「跳级连对」两类，
跨组这一类漏了，而它比另外两类更危险 —— 跨组成立的「连对」会拿 `cards[0]` 的组
去参与 `_can_beat_lead`，于是副级对冒充主牌连对，压过真正的同花连对。

### 改法

1. **序列定义集中到一处**：`trump.sequence_index(card, trump) -> int | None`
   —— 牌在「本组连对序列」中的位置；级牌 / 副级 / 王返回 `None`。
   墩赢家（`trick._is_tractor`）与合法枚举（`legal._tractors`）**共用它**。
2. **`structure_of` / `structure_matches` 的 `trump` 改为必需参数**，不给默认值。
   理由：不给主牌信息只能退回裸点数相邻，而「忘了传」若能被默认值掩盖，
   就等于把这次修掉的缺陷重新埋回去。让它在调用点报错。
3. **修掉枚举的单向盲区**：`_tractors` 原先按「花色 + 裸点数」切段再回验。
   回验（§3 的自洽校验）只能挡**多生成**、挡不住**漏生成** ——
   跳级连对根本生成不出来，于是出现「枚举说没有这一手、赢家判定说它是连对」。
   现改为按 `sequence_index` 切段。
4. `RuleProfile.tractor_skips_level` 由 `False` 改 `True` 并重写说明：
   它现在如实记录引擎行为，但仍属 `UNVERIFIED`；要改只改 `sequence_index` 一处。

### 与 §10 判断的关系（记录下来，避免下次再犯）

§10 的结论「六项前置全缺 → 排在所有现场标定之后」在 §6 已被推翻过一次；
这次是**同一类错误的第二次**：把「取值未知」误当成「不能开发」。
两次的共同教训是 —— **先问「这条规则的不确定性，会不会改变判定的结构」**。
不会的（跨组、层次）直接写；会改变结构的（挖掉后是否接上）做成插槽。

### 残留

Phase 0 仍需确认的只剩**取值本身**：级牌挖掉后前后是否接上（即 ♠J♠J+♠9♠9 能否
作为连对打出）。复核方式见 `todo.md` 的 Phase 0 清单。
