## 1. 背景与目标

在 QQ 游戏「升级」（又名拖拉机 / 双升 / 80 分）对局中，实时自动记牌，减轻人脑记忆负担。

**核心目标**：在对局进行中，自动、可靠地维护一份「牌局全局状态」，并展示：

| 编号 | 功能 | 说明 |
|---|---|---|
| A | 剩余牌清单 | 每个点数/花色还剩几张未出现 |
| B | 按家记牌 | 谁打出了什么，推断各家各自可能持有的牌 |
| C | 分数与墩次追踪 | 当前分数、分牌归属、墩次边界 |

**明确不做（非目标）**：
- 不做 D 出牌建议 / 胜率提示
- 不做 E 牌局记录与复盘
- 不做找朋友模式
- 不做安装包、自动更新、对外发布

## 2. 已确认的需求决策

| 决策项 | 选择 | 影响 |
|---|---|---|
| 数据获取方式 | **屏幕截图 + 图像识别** | 不碰游戏进程、不注入内存，风险等级最低；需处理识别误差 |
| 功能范围 | A + B + C | 需识别「谁打出了什么」+ 墩边界 |
| 使用对象 | 自用 | 无需安装器/自动更新/兼容性打磨 |
| 技术栈 | **Python + OpenCV** | uv 管理依赖，虚拟环境在项目目录 |
| 玩法变体 | **两副牌 + 三副牌都要支持** | 引擎必须参数化，见 §7 |
| 结果显示 | **独立置顶小窗**（可配置位置） | 半透明无边框，不遮牌面 |
| 识别兜底 | **不确定就提醒 + 手动纠正** | 置信度低时中断自动流程，不静默算错 |
| 游戏窗口模式 | 窗口化 / 无边框窗口 | 抓屏可靠，置顶小窗可正常叠加 |

## 3. 实测依据（本机实测，非估算）

所有数据来自 `spike/` 下的实测脚本，原始输出见 `spike/_bench_result.json`。

| 测量项 | 实测值 | 结论 |
|---|---|---|
| dxcam 单次 `grab()`（无新帧） | **0.038 ms** | 轮询本身几乎零成本 |
| 热路径（抓帧 + N 区灰度化 + 差分 + 判稳） | **0.042 ms/帧** | 60 FPS 下仅耗 2.5 ms/s ≈ **单核 0.25%** |
| `grab()` 无变化时的返回值 | **`None`** | OS 免费提供变化侦测，无需主动比对全屏 |
| 面板刷新率 / 屏幕真实内容变化率 | 60 Hz / **46.3 Hz** | 内容变化率是采样上限的硬约束 |
| dxcam 实际抓到的新帧率 | **46.7 FPS**（命中率 86.2%） | 与真值吻合 → **dxcam 基本不丢帧** |
| mss 整屏 BitBlt（兜底方案） | 17.7 ms = **56 FPS** | 可用但**吃掉约一个核心**，属降级模式 |
| matchTemplate 单次（角标 30×22 在牌面 70×100 内搜索） | 0.145 ms | 见下方成本模型 |

### 3.1 识别成本模型（本稿修正）

初稿把「8 张牌 × 54 类模板 ≈ 63 ms/墩」当作单墩成本，这是错的——若每帧都做全量识别，
7 帧投票 = **约 440 ms/墩**。

**修正方案：把"一张牌是什么"拆成两个独立分类器**

| 分类器 | 类别数 | 说明 |
|---|---|---|
| 点数分类器 | **13** | A,2..10,J,Q,K（角标数字/字母） |
| 花色分类器 | **4** | ♠♥♦♣（角标花色符号） |

每张牌只需 13 + 4 = **17 次匹配**，而非 54 次。

**成本必须以「本区牌张数」为单位表达**（识别是逐区进行的，见 §5.1 `recognize(zone)`）：

```
单区单帧成本 = cards_in_zone × 17 × 0.145 ms
单墩成本     = Σ_zone( cards_in_zone × 17 × 0.145 ms ) × 3 帧投票
```

| 场景 | 单区牌数 | 单区单帧 | **单墩成本** |
|---|---|---|---|
| 4 人·常态（每区 1 张） | 1 | 2.5 ms | **29.6 ms** |
| 4 人·最坏（每区甩牌 8 张） | 8 | 19.7 ms | **236.6 ms** |
| 6 人·常态（每区 1 张） | 1 | 2.5 ms | **44.4 ms** |
| 6 人·最坏（每区甩牌 8 张） | 8 | 19.7 ms | **355.0 ms** |

> 初稿此处残留了「8 张牌/帧」这一 4 人假设（来自被废弃的整桌识别方案）。
> 6 人 3 副变体下区数与每区牌数都不同，故必须按上式重算。

**投票策略**：只对 **3 帧**（而非 7 帧）做识别并逐张多数投票；其余帧仅用于判稳检测。
即使最坏情况 355 ms/墩，而每墩间隔数秒，占空比仍 **< 5%**，CPU 压力可忽略。

> **踩坑记录**：早期一次测量得出 "dxcam 只有 12 FPS"，是**测量方法缺陷**（用 `latest_frame_ticks` 计数）造成的假象。后续用 mss 作为地面真值交叉验证，确认 dxcam 实际为 46.7 FPS。设计结论以地面真值版本为准。

## 4. 采集与采样设计

### 4.1 核心思路：变化驱动，而非定时截屏

dxcam 底层为 Desktop Duplication API，`grab()` 在屏幕未变化时返回 `None` 且仅耗 0.038 ms。
因此不需要"定时截图再比对"，只需高频询问"变了吗"。

### 4.2 两种运行模式

| 模式 | 条件 | 轮询间隔 | 单帧成本 | CPU 占用 |
|---|---|---|---|---|
| **采集中** | 游戏窗口存在且未最小化 | **16.7 ms（60 Hz）** | 0.038 ms（无变化）/ 0.042 ms（有变化） | ≈ **0.25% 单核** |
| **挂起** | 窗口最小化 / 不存在 / 用户暂停 | 200 ms（5 Hz） | 同上 | ≈ 0.02% 单核 |

**变化侦测与 ROI 的关系（本稿澄清）**：

- **变化侦测用全输出抓帧**（`grab(region=None)`，即整个显示器），因为 Desktop Duplication
  的"是否有新帧"判据是**整个输出**级别，无法只订阅某几个矩形
- **识别时才切 ROI**：拿到全帧后在 numpy 里切片（切片成本可忽略，见 §3）
- 因此 §3 表中 `grab()` 的 0.038 / 0.042 ms **均为全输出测量值**，已包含这个模式的成本
- 代价：显示器上**任何**区域变化都会产生新帧，即使与本游戏无关。这由 §4.3 的
  逐区差分吸收——非目标区域的变化不会让任何区离开 `EMPTY`

> 初稿曾设"IDLE 100 Hz / ACTIVE 60 Hz"两档，但该分档**成本是反的**（100 Hz 比 60 Hz 更贵）。
> 由于无变化时 `grab()` 本就瞬时返回 `None`，**无需为"没事发生"设更慢的档位**。
> 简化为：恒定 60 Hz 轮询，差异只体现在"拿到新帧后做什么"。真正的省电档只用于窗口挂起时。

### 4.3 出牌事件的状态机（每区独立）

**区数 N = 玩家数**（4 人或 6 人），不得硬编码。

```python
class ZoneState(Enum):
    EMPTY     = "empty"      # 该区无牌
    ENTERING  = "entering"   # 检测到变化，动画进行中
    SETTLED   = "settled"    # 连续 8 帧差异 < 阈值，牌已摆定
```

```
EMPTY ──变化──> ENTERING ──连续8帧差异<阈值──> SETTLED
                   │                              │
                   └──判稳前又变化──> missed_play   │
                                                  ▼
                            识别（3帧投票 + pHash 去重）
                                                  │
                        全部 N 区同时回到 EMPTY ───┘ → 一墩结束
```

> 命名说明：初稿的 `IDLE/STABLE` 与采样档位**同名冲突**，本稿区分为
> 采样侧 `采集中/挂起` 与区域侧 `ZoneState.EMPTY/ENTERING/SETTLED`。

- **只在 `SETTLED` 状态识别**，避免截到动画中间态
- **3 帧多数投票**（奇数防平票）
- **pHash 去重**：哈希未变 = 同一墩，跳过，从机制上杜绝重复计数

### 4.4 "牌只显示几秒"的余量核算

```
最短显示 2 秒 → 60 Hz × 2 s = 120 帧可用
需求：判稳 8 帧 + 投票 3 帧 = 11 帧
余量 ≈ 10 倍
```

极限情况（20 Hz + 1.5 秒显示）仍有 30 帧，足够。

### 4.5 两道兜底

1. **环形缓冲**：常驻最近 3 秒的 ROI 灰度缩略帧。
   容量 = `N 区 × 300×100 像素 × 180 帧 × 1 字节`。
   4 人局 ≈ **21.6 MB**；6 人局 ≈ **32.4 MB**。
2. **看门狗**：判稳完成前区域又变化 → 记 `missed_play`，悬浮窗标黄提示手动补录。
   **宁可让用户点一下，也不静默算错。**

### 4.6 墩边界自动识别

一墩结束时 **全部 N 个出牌区同帧清空**。"N 区同时变化"信号免费获得，作为功能 C 的分墩依据。

### 4.7 底牌与亮主：短暂显示的特例

- **底牌/扣底区**只有**庄家**可见，且仅在对局开始后短暂显示
- **亮主/反主指示区**变化频率低但必须捕捉
- 二者都复用 §4.3 的同一套状态机与 §4.5 的环形缓冲，不做特殊处理

### 4.8 磁盘落盘策略

- 每次出牌事件：仅存 1 张投票后的稳定帧 PNG
- **仅当置信度 < 阈值**：才保存该次 3 帧完整爆发，供调试与模板挖掘
- **粒度与上限（本稿澄清）**：4 人局一局约 25 墩 ≈ **100 次出牌**，故 200 手 ≈ 2 局。
  正常模式约 0.2 MB/手 → 一局 ≈ 20 MB。
  低置信爆发保存的实际上界是**本局出牌数**（≈100），截图上限"200 次/局"因此永远不会触发；
  真正的硬上限应为 `min(200, 本局出牌数)`，且**同时覆盖 `missed_play` 与 `low_confidence`**
  两类爆发。超出后只存计数与元数据，并在 UI 提示"证据保存已达上限"
- 所有落盘文件按 `deal_id/trick_index/seat` 组织，便于 L3/L4 离线回放取用

## 5. 架构

```
┌──────────────────────────────────────────────────────┐
│ UI 层  PySide6 无边框置顶小窗（N 家面板）              │
│  剩余牌统计 │ 各家推断 │ 墩次/分数 │ 低置信提醒+纠正   │
├──────────────────────────────────────────────────────┤
│ 牌局引擎  纯 Python，零 IO，纯状态迁移，可离线回放     │
│  牌张模型/主牌判定 │ Deal 状态机 │ 记牌与各家范围推理   │
│  墩赢家判定（跟牌/对子/拖拉机/甩牌）                   │
├──────────────────────────────────────────────────────┤
│ 事件层  时序与去重                                     │
│  N×出牌区状态机 │ 墩边界检测 │ pHash 去重 │ 环形缓冲    │
│  3 帧投票 │ 置信度评估                                  │
├──────────────────────────────────────────────────────┤
│ 识别层  Protocol: CardRecognizer（可替换）             │
│  点数分类器(13) + 花色分类器(4)                        │
│  TemplateRecognizer(OpenCV, 现在) │ CNN(预留) │ OCR校验 │
├──────────────────────────────────────────────────────┤
│ 采集层  Protocol: CaptureBackend（可替换）             │
│  DxcamBackend(Desktop Duplication, 主) │ Mss(BitBlt 降级)│
├──────────────────────────────────────────────────────┤
│ 校准与配置  一次性 ROI 标定 → JSON                      │
│  窗口定位(win32) → 客户区归一化坐标 → 区→座位映射        │
└──────────────────────────────────────────────────────┘
```

### 5.1 关键接口与载荷

```python
# ---- 可替换接口 ----

class CaptureBackend(Protocol):
    def grab(self, region: Region | None) -> Frame | None: ...
    def close(self) -> None: ...

class CardRecognizer(Protocol):
    def recognize(self, zone: GrayFrame) -> RecognitionResult: ...

# ---- 变体规则（§7.1）与运行时配置（§11.2）是两个不同层次，本稿明确区分 ----

@dataclass(frozen=True)
class VariantRule:
    """静态规则数据：某个 (players, decks) 变体的固定属性。"""
    players: int
    decks: int
    hand_size: int
    bottom_size: int
    source: str            # "measured" | "documented" | "UNVERIFIED"

@dataclass(frozen=True)
class Thresholds:
    min_card_score: float      # 逐张置信度下限
    min_frame_agreement: float # 3 帧一致率下限

@dataclass(frozen=True)
class GameConfig:
    """从 §11.2 JSON 载入的运行时配置，供引擎与 UI 共同使用。"""
    rule: VariantRule
    level_rank: int                        # 当前级数 2..14，见 §7.6.2
    zone_to_seat: tuple[int, ...]          # 区索引 -> 座位索引
    turn_direction: Literal["cw", "ccw"]
    first_lead_seat: int
    thresholds: Thresholds

@dataclass(frozen=True)
class TrumpInfo:
    kind: Literal["suit", "no_trump"]
    suit: int | None                       # kind=="suit" 时为主花色
    level_rank: int                        # 冗余自 GameConfig，便于比较函数自洽
    jokers_as_trump: bool = True

@dataclass(frozen=True)
class PendingItem:
    """§9.1 待确认队列条目。"""
    frame_ts: float
    reason: Literal["low_confidence", "missed_play"]
    seat: int
    proposed_cards: tuple[Card, ...]       # 低置信时的候选；missed_play 时为空
    confidence: float
    frame_agreement: float
    evidence_path: str                     # 入队时即落盘的证据帧

# ---- 牌张编码 ----

@dataclass(frozen=True)
class Card:
    rank: int          # 2..14，其中 J=11 Q=12 K=13 A=14（A 大于 K，见 §7.6）
    suit: int          # 0..3 = ♠♥♦♣
    joker: int | None  # None / 1=小王 / 2=大王；非 None 时 rank/suit 无意义

@dataclass(frozen=True)
class RecognitionResult:
    cards: tuple[Card, ...]
    confidence: float                      # = min(per_card_scores)，见下方门槛定义
    per_card_scores: tuple[float, ...]
    frame_agreement: float                 # 3 帧投票一致率 0.0~1.0

@dataclass(frozen=True)
class PlayEvent:
    seat: int              # 座位索引 0..N-1
    cards: tuple[Card, ...]
    confidence: float
    trick_index: int
    frame_ts: float        # 采集时间戳
    evidence_path: str | None   # 低置信时保存的爆发帧路径

@dataclass(frozen=True)
class GameState:
    config: GameConfig
    trick_index: int
    current_player: int
    trump: TrumpInfo               # 主牌花色 / 无主 / 大小王对
    unseen: Mapping[Card, int]     # 未见牌池计数
    per_seat_candidates: tuple[frozenset[Card], ...]   # 功能 B：最紧可靠超集
    per_seat_certain: tuple[frozenset[Card], ...]      # 必然持有（可空）
    tricks_won: tuple[int, ...]
    points: tuple[int, ...]
    phase: DealPhase
    pending: tuple[PendingItem, ...]   # 待确认队列，见 §9.2
```

**低置信门槛是「两个独立阈值的合取」（本稿澄清）**：

```
触发人工纠正  ⟺  confidence < min_card_score
                 OR  frame_agreement < min_frame_agreement
```

即**任一不达标**即触发，而非取平均。`confidence` 字段本身定义为 `min(per_card_scores)`
（整区最低单张分），`frame_agreement` 单独成字段，避免把两个不同来源的量混成一个数。

### 5.2 三个刻意的解耦决定

1. **牌局引擎不碰任何 IO** —— 纯状态迁移函数。规则、计分、记牌推理可 100% 单元测试，也能用录制帧离线回放验证。
2. **采集器与识别器都是 Protocol 接口** —— dxcam 失效自动降级 mss；模板匹配到瓶颈可直接换 CNN，上层不改。
3. **采集线程与 UI 线程分离**，通过队列传事件 —— 悬浮窗卡顿绝不丢帧。

## 7. 牌局引擎

### 7.1 变体规则表（本稿修正）

初稿声称"底牌张数与每人手牌数由 `(decks, players)` 推导"，这与"必须实测确认"自相矛盾。
**修正：`(decks, players)` 不是自由笛卡尔积，而是一张需要外部规则数据的查找表。**

```python
# VariantRule 定义见 §5.1
VARIANT_RULES: dict[tuple[int, int], VariantRule] = {
    (4, 2): VariantRule(4, 2, 25, 8,  source="documented"),   # 25×4 + 8 = 108 ✓
    (6, 3): VariantRule(6, 3, 25, 12, source="UNVERIFIED"),   # 需 Phase 0 实测
    # (5, 2) 存在但不在本项目范围
}
```

**范围界定**：
- 本项目支持两个变体：`(4 人, 2 副)` 与 `(6 人, 3 副)`
- `(4,2)` 的 25 手牌 + 8 底牌已由官方规则确认（合计 108 张 ✓）
- `(6,3)` 的 12 张底牌标注为 **`UNVERIFIED`**，引擎在收到未验证变体时必须**拒绝启动并提示标定**，
  而非采用猜测值。**Phase 0 的验收项包含补齐这张表**（见 §14）。
- 5 人局不实现

### 7.2 牌局阶段状态机

```
DEAL（发牌） → DECLARE（亮主） → COUNTER_DECLARE（反主）
  → BOTTOM（扣底/看底牌） → PLAY（出牌，逐墩） → SCORE（收分/算分） → LEVEL_UP（升级）
```

对外只暴露：`apply(event) -> GameState` 与 `GameState` 快照。

### 7.3 墩赢家判定 —— **明确在范围内**

功能 C（分牌归属）要求知道每墩谁赢，因此**必须实现完整的墩赢家逻辑**，这是引擎中最大的一块：

- 跟牌规则（有该花色必须跟，无则可用主牌/垫牌）
- 对子、连对（拖拉机）、甩牌的合法性
- 主牌与副牌的比大小（含大小王、主牌花色、无主局）
- 首出方与出牌顺序（顺时针/逆时针由校准配置决定）

> 评审意见已采纳：初稿把这块含糊地写成"规则、计分、主牌判定"。本稿明确其为 C 的前置依赖
> 与 Phase 3 的主要工作量。

### 7.4 记牌推理（功能 B）—— 输出契约与底牌记账

#### 7.4.1 记账模型（第 4 次修正；原公式有两类重复扣减缺陷）

**术语定义**（4 人 2 副为例）：

| 符号 | 含义 | 大小 |
|---|---|---|
| `A_i` | 发牌时座位 i 的手牌 | 25 |
| `P` | 发牌后、扣底**前**的底牌 | 8 |
| `H` | 庄家扣底**后**的最终手牌 | 25 |
| `D` | 庄家扣底**后**底牌中的牌（庄家自选，故庄家知道） | 8 |

关系：`H = (A₀ ∪ P) − D`，且 `D ⊆ A₀ ∪ P`，故 **`H ∩ D = ∅`**。

**缺陷一：两个快照必须取自同一时点**

`known = hand_snapshot ∪ bottom_snapshot` 仅在两者互斥时成立：

- ✅ 扣底前组合：`A₀ ∪ P` = 33 张，互斥
- ✅ 扣底后组合：`H ∪ D` = 33 张，互斥
- ❌ **混用**（扣底后的 `H` + 扣底前的 `P`）：`H ∩ P = P − D`，即庄家留下的底牌，**非空**
- 注意 `A₀ ∪ P = H ∪ D`，两种写法的集合**完全相同**，但**不能交叉取**

**本设计采用的组合：扣底后 (`H`, `D`)**。理由：这两个区域在出牌阶段持续可见、可反复校验；
而扣底前的 `P` 只在一瞬间可见，可靠性差。

构造 `known` 时的断言：

```
|H| == hand_size
|D| == bottom_size
H ∩ D == ∅
|H ∪ D| == hand_size + bottom_size
```

任一断言失败 → 判定为识别错误，走 §9 流程。

**缺陷二：`played` 与 `known` 重叠**

初稿 `unseen = full_deck − known − played` 是错误的：`played` 包含**用户自己打出的牌**，
而这些牌本就在 `known` 中，会被扣减两次，使 `unseen[c]` 变成负数。

**修正为实时多重集计数器**：

```
初始化:            unseen[f] = copies_in_deck(f) − copies_in_known(f)
每个公开出牌事件:  对该事件打出的每张牌 f:
                     若该牌来自「手牌 ⊆ known」的座位（即用户自己）→ 不扣减
                     否则                                      → unseen[f] -= 1
```

**不变式（必须始终成立，同时是识别错误探测器）**：

| # | 不变式 | 含义 |
|---|---|---|
| I1 | `unseen[f] >= 0` 对所有 f | 出负数说明识别重复或错认 |
| I2 | `sum(unseen) == 其他座位持牌总数 + 未知底牌数` | 总账平衡 |

任一不变式被破坏 → 判定为识别错误，走 §9 流程。

**缺陷三：非庄家时底牌不属于任何一家，必须显式建模**

非庄家时 8 张底牌停留在 `unseen` 中，但**不属于任何座位的手牌**。
若不保留这个"槽位"，计数约束会把底牌派给某家，使 `certain[seat]` 包含实际在底牌里的牌，
从而破坏 §10.1 的 B2 断言（`certain[seat] ⊆ ground_truth[seat]`）。

**修正**：知识模型必须含一个显式的**容量受限未知牌堆** `bottom_unknown`：

| 用户身份 | `bottom_unknown` 容量 | `known` 大小（4 人 2 副） |
|---|---|---|
| 庄家 | **0**（底牌已被 `D` 覆盖，完全已知） | 33 = 25 + 8 |
| 非庄家 | **bottom_size = 8** | 25 |

推断只在 `{others[seat]}` ∪ `{bottom_unknown}` 这些堆之间做**容量受约束的强制分配**，
容量参与求解。底牌区不可见时 `bottom_unknown` 容量不变，**不报警**（§9）。

#### 7.4.2 输出契约

- **`per_seat_candidates[seat]`（最紧可靠超集）**：定义为
  *「在所有与已记录事件历史一致的牌局世界中，`seat` 可能持有的牌的并集」*。
  必须满足 **`ground_truth[seat] ⊆ candidates[seat]`**（soundness）。
- **`per_seat_certain[seat]`（必然持有）**：能由约束推导出必然在该家的牌。必须满足
  **`certain[seat] ⊆ ground_truth[seat]`**。允许为空集。

**明确不做概率推断**：不输出每张牌的概率或期望值（YAGNI，且无客观验收标准）。

#### 7.4.3 为什么必须定义"最紧"

仅要求 `ground_truth ⊆ candidates` 是**可被平凡满足的**——直接返回整个 `unseen` 池给每一家
就恒成立，等于没有实现任何推断。因此 §10 与 §14 的验收必须同时包含
**排除性断言**（可证必然在别家的牌，不得出现在本家 candidates 中），
详见 §10 功能 B 专项验收。

### 7.5 座位与出牌方向

- 区→座位映射**不是**隐式约定，而是校准配置的一部分（客户端座位方位与出牌方向不一定固定）
- 配置项：`zone_to_seat: list[int]`、`turn_direction: "cw" | "ccw"`、`first_lead_seat`
- 4 人局区名使用屏幕方位（`bottom`=自己 / `left` / `top` / `right`）；6 人局由标定流程按实际布局生成

### 7.6 牌张大小与主牌次序约定（第 4 次修正；原版遗漏级牌）

#### 7.6.1 级牌 —— 原版缺失，且会直接导致墩赢家判错

升级中**当前级数所对应的点数是主牌**。设当前级数为 `L`（例如打 2 时 `L=2`）：

- **正级** = 主牌花色的 `L`（主牌为 ♠、`L=2` → ♠2），**仅次于大小王**
- **副级** = 其余三门的 `L`（♥2 ♦2 ♣2），**高于主牌花色的 A**

完整次序（从大到小）：

```
大王 > 小王
     > 正级（主花色 L）
     > 副级（其余三门的 L）
     > 主花色 A > K > Q > J > 10 > ... > 2   （跳过 L）
     > 任意副牌（每门内 A > K > ... > 2）
```

- **无主局**：大小王为主牌；四门 `L` 均为主牌
- 对子、连对（拖拉机）比较要求**结构相同**，并遵循同一次序

#### 7.6.2 级的来源与存放

| 项 | 说明 |
|---|---|
| 存放 | `GameConfig.level_rank: int`（2..14），与 `TrumpInfo` 一同作为主牌判定的输入 |
| 来源优先级 | ① 用户手动指定/纠正 > ② 主牌指示区 ROI 识别 > ③ 上局升级结果推算 |
| 更新时机 | §7.2 的 `LEVEL_UP` 阶段在每局结束时更新 |

#### 7.6.3 待验证项（Phase 3a 前置）

⚠️ **副级三门之间是否可互相比较**，不同规则集有差异。本设计**默认按 §7.6.1 的次序**
（即副级之间同级、不可互压）实现，但**必须用实际客户端对局验证**——它直接决定
墩赢家与分牌归属（功能 C 的核心）。若实测为其他规则，比较函数需相应调整。

该次序表是 §7.3 墩赢家判定的唯一权威来源，不在他处重复定义。

## 8. 数据流与线程模型

```
采集线程 ──帧──> 事件线程 ──PlayEvent──> 引擎 ──GameState──> Qt 信号 ──> UI 线程
   │                  │
 60 Hz          识别（仅在 SETTLED 触发）
环形缓冲        3 帧投票 ≈ 29.6 ms/墩（4 人常态，见 §3.1）
```

- 采集线程：唯一调用 `grab()` 的线程
- 事件线程：差分、区域状态机、调用识别器
- 引擎：被事件线程同步调用（纯计算，快）
- UI：Qt 主线程，仅通过信号槽接收状态快照

## 9. 错误处理

| 失败模式 | 检测方式 | 处置 |
|---|---|---|
| 识别置信度低于阈值 | `confidence < min_card_score` **或** `frame_agreement < min_frame_agreement`（§5.1） | 进入 §9.1 待确认队列；采集与状态机**不中断** |
| 出牌一闪而过 | 判稳前区域又变化 | 记 `missed_play` 入 §9.1 待确认队列（`reason=missed_play`） |
| ROI 被遮挡 | 识别结果与所有已知牌型均不匹配 | 报警"牌桌区被遮挡"，提示移开窗口 |
| **底牌区不可见/为空** | — | **正常状态，不报警、不做任何扣减**（见 §7.4.1） |
| `known` 集合断言失败 | `\|known\|` 不符或 hand∩bottom ≠ ∅ | 视为识别错误，走低置信流程 |
| 窗口移动/缩放 | 运行时校验窗口矩形 | 按比例重算 ROI；尺寸不符则提示重新标定 |
| 窗口最小化/失焦 | win32 窗口状态查询 | 进入**挂起模式**（5 Hz），悬浮窗显示"已暂停" |
| dxcam 初始化失败 | 启动自检 | 降级 mss，**进入降级模式**（见下） |
| 牌局阶段误判 | 无法推进状态机 | 提供"手动重置本局"入口 |
| 显示器切换 | 窗口所在 output 变化 | 按窗口位置重选 `output_idx` |
| 未验证变体（如 6 人 3 副） | 查 §7.1 规则表 | 拒绝启动并提示先完成标定实测 |

### 9.1 低置信度暂停的语义（本稿补充，防止静默丢牌）

初稿只写"暂停自动流程"，但未定义暂停期间采集与状态机是否继续，存在**静默丢牌**风险：
§4.5 的环形缓冲只保留约 3 秒，而人工纠正往往超过 3 秒。

**修正后的语义**：

| 组件 | 暂停期间行为 |
|---|---|
| 采集线程 | **继续运行**（60 Hz 不变） |
| N 个区状态机 | **继续运行**，继续产出 `PlayEvent` |
| 墩边界检测 / `trick_index` | **继续运行**（否则墩序会错） |
| 引擎的**自动提交** | **门控**：不直接写入 `GameState` |
| 事件去向 | 进入**按 `frame_ts` 排序的待确认队列** `GameState.pending` |

- **证据帧在入队时立即落盘**，不依赖只有 3 秒的环形缓冲
- 用户纠正完成后，**按 `frame_ts` 顺序重放**待确认队列
- 每个未纠正事件都是 `pending` 中的**显式条目**，绝不静默丢弃
- 看门狗产生的 `missed_play` 与低置信产生的 `pending` **共用同一队列**，
  仅 `reason` 字段不同（`low_confidence` / `missed_play`）
- UI 以待确认条数显示角标，提示用户按 §14.1 热键进入交互模式

### 9.2 mss 降级模式

mss 单帧 17.7 ms（56 FPS）**约等于一个完整核心**，与 dxcam 的 0.25% 不在同一量级。
因此降级时**不维持 60 Hz**：

- 轮询降到 **15 Hz（66 ms）**
- 判稳窗口从 8 帧延长到 **12 帧**（仍约 0.8 秒）
- UI 明确显示"降级模式（BitBlt）"

## 10. 测试策略

| 层级 | 对象 | 方法 |
|---|---|---|
| L1 | 牌局引擎 | pytest 纯单测：规则、计分、主牌判定、**墩赢家判定**、记牌推理。测试矩阵覆盖两个受支持变体 `(4,2)` 与 `(6,3)`，而非 `decks × players` 自由组合 |
| L2 | 识别器 | 录制样本集回归：输出混淆矩阵与各类准确率（点数 13 类、花色 4 类分别统计），设最低阈值门禁 |
| L3 | 事件层 | 录制帧序列**离线回放**，断言 `PlayEvent` 序列（含 `seat`/`trick_index`）与墩边界正确 |
| L4 | 端到端 | 录一段真实牌局 → 回放 → 断言最终记牌结果与人工核对一致 |

### 10.1 功能 B 的专项验收（防止平凡满足）

仅断言 `ground_truth ⊆ candidates` 不够——返回整个 `unseen` 池给每一家即可恒真。
因此必须**四条断言同时成立**：

| # | 断言 | 防的是什么 |
|---|---|---|
| B1 | `ground_truth[seat] ⊆ candidates[seat]`（每家） | soundness |
| B2 | `certain[seat] ⊆ ground_truth[seat]`（每家） | certain 的 soundness |
| B3 | **排除性**：构造场景中可证必然在别家的牌，**不得**出现在 `candidates[seat]` | **平凡全集解** |
| B4 | 构造场景中存在 `certain[seat] ≠ ∅` 的情形 | **恒返回空集解** |

- B3 的构造场景：例如某花色全部剩余牌已被别家明牌持有，则该家的 `candidates`
  中不得含该花色任何牌
- B4 的构造场景：例如某家某花色剩余张数已被"其余各家都不可能持有"逼死
- 另设**紧致度回归**：记录多个构造场景下 `|candidates|` 的基线值，
  超过基线一定比例即判定为推断退化（防止实现悄悄退化为返回全集）

### 10.2 待确认队列的验收

构造"低置信事件后紧跟正常事件"的帧序列，断言：

1. 所有事件都出现在 `pending` 队列中，**无丢失**
2. 队列按 `frame_ts` 有序
3. 重放后最终 `GameState` 与"无低置信介入"的参照序列一致

**可测性前提**：帧序列可录制/回放，因此 L3/L4 不需要真实游戏在跑。

> ⚠️ **本节已被 §11A 取代**：绝对像素坐标属"快照"而非方案，分辨率变化即失效。
> 保留此处仅为记录当时的实测观察。

- ROI 存为**相对游戏窗口客户区左上角的归一化坐标**（`0.0~1.0`），不存绝对像素
- 运行时每次窗口移动/缩放后重新换算
- **多尺度模板匹配推迟**：先不实现。自用场景下窗口尺寸固定，等真的观察到缩放需求再加，
  避免为假设情况增加标定与匹配复杂度（评审意见已采纳）
- **DPI**：进程声明 Per-Monitor DPI Aware，避免逻辑/物理坐标错位
- 配置文件：JSON，含 ROI 定义、`zone_to_seat`、显示器序号、变体选择、模板版本、阈值参数

## 11A. 通用定位方案（替代硬编码坐标）

**问题**：§11.3 的绝对像素坐标只是 1280×720 下的一个快照。窗口缩放、换分辨率、
6 人局换布局、客户端更新，都会让它失效。且失效方式往往是**静默算错**，而非报错。

**原则：不存「坐标」，存「锚点 + 相对几何 + 单位」。**

### L1 窗口锚定（必做，成本极低）

- 运行时用 win32 按窗口类名/标题定位游戏窗口，取**客户区**矩形
- 一切坐标相对客户区，而非屏幕绝对坐标
- 解决：窗口移动、跨显示器、多屏摆放差异
- 同时确定应使用哪个显示器输出（`dxcam` 的 `output_idx`）

### L2 颜色锚点 + 相对几何 + 牌张尺寸为单位（已在真实截图验证）

**① 颜色锚点** —— 桌面是独特的深蓝青色：

| 项 | 实测值 |
|---|---|
| 桌面色均值 | BGR ≈ (110, 69, 21) |
| 各通道标准差 | ≈ 10（颜色集中，可作锚点） |
| 四张截图的锚点 bbox | **逐像素完全相同**：x0 y0 1131×683，中心 (565.5, 341.5) |

分割方式：到桌面均值的欧氏颜色距离阈值（实测 45 有效）。
锚点 bbox 稳定可复现 → **不需要硬编码桌面位置**。

**② 相对几何** —— 四区是规则十字，不是 4 个独立矩形：

| 区 | 相对中心偏移 | 换算为牌张单位 |
|---|---|---|
| 上 | dx=+1.2, dy=−79.0 | (0.00, −1.00) 牌高 |
| 左 | dx=−108.8, dy=−3.0 | (−1.92, 0.00) 牌宽 |
| 右 | dx=+106.2, dy=−3.0 | (+1.90, 0.00) 牌宽 |
| 下 | dx=+1.2, dy=+85.0 | (0.00, +1.08) 牌高 |

- 左右臂对称（差 2.5px）、上下臂近似对称（差 6.0px）
- **只需 3 个数（中心 + 2 个偏移）描述四区，替代 4 个矩形的 16 个数**
- 6 人局只需换成 6 个角度/偏移，同一套机制

**③ 单位换成「牌张尺寸」** —— 这是分辨率无关的关键：

| 项 | 实测值 |
|---|---|
| 单张牌外接框 | **56 × 79 px**，宽高比 **0.709** |
| 标准扑克牌宽高比 | 2.5 : 3.5 = **0.714**（误差仅 0.5%） |
| 两张牌叠放后宽度 | 72 px → 叠放偏移 **16 px** |

所有偏移、区尺寸一律表示为**牌宽的倍数**。分辨率变化时，
只要重新自动测一次牌宽，整个布局随之缩放。

**牌宽可自动测量**：出牌区内 1 张牌 → 外接框宽 56px；2 张牌 → 72px；
由「56 + n×16」反推出牌宽与叠放偏移。也可从手牌区高度反推牌高。

### L3 在线自学习出牌区（最通用，可选）

完全不预设位置：

- 持续累积一张**占用图**，记录每个区域是否在「桌面 ↔ 牌」之间随时间反复翻转
- 反复翻转的区域即为出牌区；按相对桌心的角度聚类，自动得到 N 个区
- 优点：自动适配 4 人/6 人、客户端改版、任意分辨率，连锚点都不需要
- 代价：冷启动需观察数墩才能定型；期间需降级到 L2 或提示用户

**验收方式**：学到的区必须能产生合法牌局（出牌顺序、墩边界、`unseen ≥ 0`）。
不合法则重新学习或提示标定。

### L4 不变量自检 + 漂移告警（安全网，必做）

无论用哪层定位，都必须校验，让脆弱性**可见而非静默失败**：

| 校验项 | 判据 | 失败处置 |
|---|---|---|
| 四区关于中心对称 | 左右臂差 < 3px，上下臂差 < 3px | 告警 |
| 区尺寸合理 | ≈ 1 个牌高；宽度 ≥ 最大甩牌所需 | 告警 |
| 偏移为牌宽整数倍 | 偏差 < 0.15 牌宽 | 告警 |
| 牌宽在合理范围 | 与手牌区高度自洽 | 告警 |
| `unseen ≥ 0`（§7.4.1 I1） | 恒成立 | 判定识别错误 |
| `known` 集合大小（§7.4.1） | == hand_size + bottom_size | 判定识别错误 |
| 出牌顺序合法 | 与 `turn_direction` 一致 | 告警 |

任一结构性校验失败 → 提示「布局可能已变化，请重新标定」，而非继续静默算错。

### L5 「标定」的重新定位

不再是让用户拖矩形，而是**自动检测 + 用户确认**：

1. 自动运行 L2（或 L3）定位
2. 把检测到的区、手牌区、锚点以覆盖层画出来
3. 用户只需点「对 / 不对」，不对才进入手动微调

### 待确认前提（决定 L2 是否足够）

⚠️ **QQ 游戏窗口缩放时，牌桌是等比缩放，还是「固定尺寸 + 黑边」，或 UI 固定像素而牌桌单独缩放？**

- 若**整体等比缩放** → L2 足够
- 若**混合缩放**（UI 固定、牌桌缩放） → 需要 L3，或按元素分别标定缩放基点

**验证方法**：把游戏窗口改成另一个尺寸（最大化 / 拉小），再截 2 张有牌局面的截图。
对比「四区偏移 ÷ 牌宽」是否恒定即可判定。

## 12. 风险与未决问题

| 风险 | 等级 | 说明与缓解 |
|---|---|---|
| **反作弊 / 封号** | **未知** | ⚠️ **未能核实**。读屏方案不改进程、不注入内存，属最低风险等级。但腾讯 ACE/TP 是否覆盖 QQ 游戏平台、记牌器是否被判定违规，本会话的 web 搜索工具因 API key 失效不可用，**未能查到可靠资料**。已确认的是此类工具（勇芳记牌器、我爱记牌器等）在中文互联网公开分发且持续更新。**投入前请自行评估风险，本设计不对此作保证。** |
| ROI 被遮挡 | 中 | Desktop Duplication 捕获**整个显示器**而非单窗口。若可切换到 Windows Graphics Capture（可抓被遮挡窗口）作为第二后端。 |
| 模板样本可得性 | 中 | 模板匹配需真实牌面图像。缓解：Phase 0 先交付**采样录制工具**，用 §4.3 的变化触发逻辑自动切片存盘，打两局即可攒齐样本，无需人工抓时机。 |
| 向日葵虚拟显示驱动 | 低 | 本机装有 `OrayIddDriver`（向日葵虚拟显示器）。实测 dxcam 在其存在时工作正常，但若通过远程桌面游玩，抓屏行为可能不同，需实测。 |
| **三副牌规则数据缺失** | **中** | `(6,3)` 变体的手牌数/底牌张数未验证。引擎对未验证变体**拒绝启动**，Phase 0 负责实测补齐（见 §14）。 |
| 墩赢家逻辑复杂度 | 中高 | 跟牌/对子/拖拉机/甩牌规则是引擎最大工作量，且 C 依赖它。已在 §7.3 明确在范围内。 |
| **副级牌序未验证** | **中高** | §7.6.3：副级三门是否可互压，不同规则集有差异，**直接影响墩赢家与分牌归属**。已默认一种实现并列为 Phase 3a 前置验证项。 |
| 级牌识别遗漏 | 中 | 级牌（正级/副级）必须在 §7.6 的次序中正确体现，否则比较函数必然判错。已补充 `level_rank` 到状态模型与来源优先级。 |
| 模板匹配准确率上限 | 中 | 遮挡/重叠时掉分。缓解：可替换识别器接口，样本足够后升级 CNN；OCR 作为交叉校验。 |
| 皮肤/分辨率变更 | 低 | 自用场景下重复标定即可接受。 |

## 14. 实施分期

| 阶段 | 交付物 | 验收标准 |
|---|---|---|
| **Phase 0** | 采样录制工具 + 标定工具 | ① 能自动切出带时间戳的牌面样本切片，攒齐 13 类点数 + 4 类花色模板<br>② **实测补齐 `(6,3)` 变体规则表**（手牌数、底牌张数），将 `source` 从 `UNVERIFIED` 改为 `measured`<br>③ **实测确认"看底牌"期间手牌区的变化**：若客户端把底牌临时并入手牌显示，标定的 25 张手牌 ROI 会在构造 `known` 的那个瞬间误读（见 §11.1） |
| **Phase 1** | 采集层 + 识别层 + 事件层 | 离线回放：`PlayEvent` 序列（含 `seat`/`trick_index`）与墩边界判定正确<br>**含专项验证「全部 N 区同帧清空」假设**（§4.6）：若客户端是淡出/逐区清空，`trick_index` 会被静默污染 |
| **Phase 2** | 牌局引擎（A）+ 悬浮窗 | 按 §10 L4 方式验收：录一段真实对局 → 离线回放 → 剩余牌统计与人工核对一致 |
| **Phase 3a** | 墩赢家规则引擎 + 分数墩次（C） | 墩赢家与分牌归属正确（跟牌/对子/拖拉机/甩牌用例齐全） |
| **Phase 3b** | 按家记牌推断（B） | §10.1 的 B1–B4 四条断言全部通过 + 紧致度回归不退化 |
| **Phase 4**（可选） | CNN 识别器 / OCR 交叉校验 | 识别准确率显著优于模板匹配 |

**每个阶段的验收都基于 §10 的离线回放**，因此不需要真实对局即可验证。

### 14.1 交互模式（本稿补充，修正"穿透 vs 点击纠正"矛盾）

悬浮窗默认 **鼠标穿透**（不干扰游戏点击），但纠正流程需要点击，二者矛盾。规定：

- **默认**：`WS_EX_TRANSPARENT` + 置顶，完全穿透
- **交互模式**：全局热键（默认 `Ctrl+Alt+L`）切换。进入后穿透关闭，可用鼠标操作纠正面板
- **快速动作热键**：`Ctrl+Alt+O` 强制快照当前识别（漏抓时手动补）、`Ctrl+Alt+P` 暂停/恢复采样
- UI 在有待处理纠正时，以角标提示"有待确认项"，提示用户按热键进入交互模式
