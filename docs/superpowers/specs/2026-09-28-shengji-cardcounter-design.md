# 升级（拖拉机）记牌器 — 设计文档

- **日期**：2026-09-28
- **状态**：待评审
- **目标平台**：Windows 11（本机 26200，RTX 5060 Ti，双 2560×1440 @60Hz）
- **定位**：自用工具（不考虑分发、安装包、多屏适配）

---

## 1. 背景与目标

在 QQ 游戏「升级」（又名拖拉机 / 双升 / 80 分）对局中，实时自动记牌，减轻人脑记忆负担。

**核心目标**：在对局进行中，自动、可靠地维护一份「牌局全局状态」，并展示：

| 编号 | 功能 | 说明 |
|---|---|---|
| A | 剩余牌清单 | 每个点数/花色还剩几张未出现 |
| B | 按家记牌 | 谁打出了什么，推断四家各自可能持有的牌 |
| C | 分数与墩次追踪 | 当前分数、分牌归属、墩次边界 |

**明确不做（非目标）**：
- 不做 D 出牌建议 / 胜率提示
- 不做 E 牌局记录与复盘
- 不做找朋友模式
- 不做安装包、自动更新、对外发布

## 2. 已确认的需求决策

| 决策项 | 选择 | 影响 |
|---|---|---|
| 数据获取方式 | **屏幕截图 + 图像识别** | 不碰游戏进程、不注入内存，风险等级最低；需处理识别误差 |
| 功能范围 | A + B + C | 需识别「谁打出了什么」+ 墩边界 |
| 使用对象 | 自用 | 无需安装器/自动更新/兼容性打磨 |
| 技术栈 | **Python + OpenCV** | uv 管理依赖，虚拟环境在项目目录 |
| 玩法变体 | **两副牌 + 三副牌都要支持** | 引擎必须参数化，见 §7 |
| 结果显示 | **独立置顶小窗**（可配置位置） | 半透明无边框，不遮牌面 |
| 识别兜底 | **不确定就提醒 + 手动纠正** | 置信度低时中断自动流程，不静默算错 |
| 游戏窗口模式 | 窗口化 / 无边框窗口 | 抓屏可靠，置顶小窗可正常叠加 |

## 3. 实测依据（本机实测，非估算）

所有数据来自 `spike/` 下的实测脚本，原始输出见 `spike/_bench_result.json`。

| 测量项 | 实测值 | 结论 |
|---|---|---|
| dxcam 单次 `grab()`（无新帧） | **0.038 ms** | 轮询本身几乎零成本 |
| 生产热路径（抓帧 + 4 区灰度化 + 差分 + 判稳） | **0.042 ms/帧** | 跑满 60 FPS 仅耗 2.5 ms/s ≈ **单核 0.25%** |
| `grab()` 无变化时的返回值 | **`None`** | OS 免费提供变化侦测，无需主动比对全屏 |
| 面板刷新率 / 屏幕真实内容变化率 | 60 Hz / **46.3 Hz** | 内容变化率是采样上限的硬约束 |
| dxcam 实际抓到的新帧率 | **46.7 FPS**（命中率 86.2%） | 与真值吻合 → **dxcam 基本不丢帧** |
| mss 整屏 BitBlt（兜底方案） | 17.7 ms = **56 FPS** | 可用，但比 dxcam 慢约 400 倍 |
| 模板匹配单次（角标 30×22 在牌面内搜索） | 0.145 ms | 8 张牌 × 54 类 ≈ **63 ms/墩** |

> **踩坑记录**：早期一次测量得出 "dxcam 只有 12 FPS"，是**测量方法缺陷**（用 `latest_frame_ticks` 计数）造成的假象。后续用 mss 作为地面真值交叉验证，确认 dxcam 实际为 46.7 FPS。设计结论以地面真值版本为准。

## 4. 采集与采样频率设计

### 4.1 核心思路：变化驱动，而非定时截屏

dxcam 底层为 Desktop Duplication API，`grab()` 在屏幕未变化时返回 `None` 且仅耗 0.038 ms。因此**不需要"定时截图再比对"**，只需高频询问"变了吗"。

### 4.2 三档自适应采样

| 档位 | 触发条件 | 轮询间隔 | 单帧成本 | CPU 占用 |
|---|---|---|---|---|
| **IDLE** | 默认 | 10 ms（100 次/秒） | 0.038 ms，多数立即返回 `None` | ≈ 0.4% 单核 |
| **ACTIVE** | 任一 ROI 检测到变化 | **16.7 ms（60 Hz）** | 0.042 ms | ≈ 0.25% 单核 |
| **SETTLE** | 连续 8 帧差异 < 阈值 | 同上（60 Hz） | 同上 | 同上 |

**上限为什么是 60 Hz**：面板物理刷新率 60 Hz，每秒最多产生 60 张不同图像（实测内容变化 46.3 Hz）。超过 60 只能拿到重复帧，无收益。

**为什么不用更低频率**：该档位决定"判定牌已摆定"的**时间分辨率**。10 Hz 下 8 帧判稳需 800 ms，凭空引入 0.7 秒延迟；60 Hz 下仅需 **133 ms**。既然成本仅 0.25% 单核，没有理由节省。

### 4.3 出牌事件的状态机

每个出牌区独立维护状态机：

```
IDLE ──变化──> APPEAR ──连续8帧差异<阈值──> STABLE ──4区同时清空──> IDLE
                  │                          │
                  └──判稳前又变化──> missed_play（报警）
                                             │
                                    识别 + 7帧投票 + pHash去重
```

- **只在 STABLE 状态识别**，避免截到动画中间态
- **7 帧等间隔多数投票**（奇数防平票）
- **pHash 去重**：哈希未变 = 同一墩，跳过，从机制上杜绝重复计数

### 4.4 "牌只显示几秒"的余量核算

```
最短显示 2 秒 → 60 Hz × 2 s = 120 帧可用
需求：判稳 8 帧 + 投票 7 帧 = 15 帧
余量 ≈ 8 倍
```

极限情况（20 Hz + 1.5 秒显示）仍有 30 帧，足够。

### 4.5 两道兜底

1. **环形缓冲**：常驻最近 3 秒的 ROI 灰度缩略帧（4 区 × 300×100 × 180 帧 ≈ **21.6 MB**）。置信度低时可倒回重算，不依赖"当时恰好抓到"。
2. **看门狗**：判稳完成前区域又变化 → 记为 `missed_play`，悬浮窗标黄提示手动补录。**宁可让用户点一下，也不静默算错。**

### 4.6 墩边界自动识别

一墩结束时 4 个出牌区**同帧清空**。"4 区同时变化"信号免费获得，作为功能 C（墩次追踪）的分墩依据。

### 4.7 磁盘落盘策略

- 每次出牌事件：仅存 1 张投票后的稳定帧 PNG
- **仅当置信度 < 阈值**：才保存该次 7 帧完整爆发，供调试与模板挖掘
- 上限：一局约 200 手 ≈ 40 MB

## 5. 架构

```
┌──────────────────────────────────────────────────────┐
│ UI 层  PySide6 无边框置顶小窗（可配置位置、鼠标穿透）  │
│  剩余牌统计 │ 各家推断 │ 墩次/分数 │ 低置信提醒+纠正   │
├──────────────────────────────────────────────────────┤
│ 牌局引擎  纯 Python，零 IO，纯状态迁移，可离线回放     │
│  牌张模型/主牌判定 │ Deal 状态机 │ 记牌与各家范围推理   │
├──────────────────────────────────────────────────────┤
│ 事件层  时序与去重                                     │
│  4×出牌区状态机 │ 墩边界检测 │ pHash 去重 │ 环形缓冲    │
│  多帧投票 │ 置信度评估                                  │
├──────────────────────────────────────────────────────┤
│ 识别层  Protocol: CardRecognizer（可替换）             │
│  TemplateRecognizer(OpenCV, 现在) │ CNN(预留) │ OCR校验 │
├──────────────────────────────────────────────────────┤
│ 采集层  Protocol: CaptureBackend（可替换）             │
│  DxcamBackend(Desktop Duplication, 主) │ Mss(BitBlt 兜底)│
├──────────────────────────────────────────────────────┤
│ 校准与配置  一次性 ROI 标定 → JSON                      │
│  窗口定位(win32) → 客户区归一化坐标 → 多尺度适配         │
└──────────────────────────────────────────────────────┘
```

### 5.1 关键接口（Protocol）

```python
class CaptureBackend(Protocol):
    def grab(self, region: Region) -> Frame | None: ...
    def close(self) -> None: ...

class CardRecognizer(Protocol):
    def recognize(self, zone: GrayFrame) -> RecognitionResult: ...
    # RecognitionResult: cards, confidence, per_card_scores

class EventSink(Protocol):
    def on_play(self, ev: PlayEvent) -> None: ...
    def on_trick_end(self, ev: TrickEndEvent) -> None: ...
    def on_uncertain(self, ev: UncertainEvent) -> None: ...
```

### 5.2 三个刻意的解耦决定

1. **牌局引擎不碰任何 IO** —— 纯状态迁移函数。规则、计分、记牌推理可 100% 单元测试，也能用录制帧离线回放验证。
2. **采集器与识别器都是 Protocol 接口** —— dxcam 失效自动降级 mss；模板匹配到瓶颈可直接换 CNN，上层不改。
3. **采集线程与 UI 线程分离**，通过队列传事件 —— 悬浮窗卡顿绝不丢帧。

## 7. 牌局引擎（参数化）

**关键设计约束**：引擎必须由 **(牌副数, 玩家数)** 参数化驱动，**不得硬编码 108 张 / 4 人**。

依据：升级规则中「每两名玩家增加一副牌」——4 人用 2 副（108 张），6 人用 3 副（162 张）。用户要求两种都支持。

```python
@dataclass(frozen=True)
class GameConfig:
    decks: int          # 2 或 3
    players: int        # 4 或 6
    point_cards: tuple  # 5, 10, K
    # 底牌张数与每人手牌数由上述参数推导，不硬编码
```

**牌局阶段状态机**：

```
DEAL（发牌） → DECLARE（亮主） → COUNTER_DECLARE（反主）
  → BOTTOM（扣底/看底牌） → PLAY（出牌，逐墩） → SCORE（收分/算分） → LEVEL_UP（升级）
```

引擎对外只暴露：`apply(event) -> GameState` 与 `GameState` 快照（供 UI 渲染）。

**记牌推理**（功能 B）：维护 full-deck 计数 − 已见牌（自己手牌 + 已打出 + 已亮底牌）= 未见牌池；再按各家弃牌历史做约束收缩，输出各家可能的牌型范围。

> ⚠️ **待实测确认**：三副牌局的具体手牌数与底牌张数（不同地方规则有差异）需在接入真实游戏后按实际 UI 校准确认，不可凭推断写死。

## 8. 数据流与线程模型

```
采集线程 ──帧──> 事件线程 ──PlayEvent──> 引擎 ──GameState──> Qt 信号 ──> UI 线程
   │                  │
 60 Hz            识别（仅在 STABLE 触发）
环形缓冲          7 帧投票 → 63 ms/墩
```

- 采集线程：唯一调用 `grab()` 的线程
- 事件线程：差分、状态机、调用识别器
- 引擎：被事件线程同步调用（纯计算，快）
- UI：Qt 主线程，仅通过信号槽接收状态快照

## 9. 错误处理

| 失败模式 | 检测方式 | 处置 |
|---|---|---|
| 识别置信度低于阈值 | 投票一致率 < 阈值 | 暂停自动流程，悬浮窗高亮 + 展示该帧画面 + 手动纠正 |
| 出牌一闪而过 | 判稳前区域又变化 | 记 `missed_play`，标黄提示手动补录 |
| ROI 被遮挡 | 识别结果与所有已知牌型均不匹配 | 报警"牌桌区被遮挡"，提示移开窗口 |
| 窗口移动/缩放 | 运行时校验窗口矩形 | 按比例重算 ROI；尺寸不符则提示重新标定 |
| 窗口最小化/失焦 | win32 窗口状态查询 | 暂停采样，悬浮窗显示"已暂停" |
| dxcam 初始化失败 | 启动自检 | 自动降级 mss（BitBlt），并在 UI 提示 |
| 牌局阶段误判 | 无法推进状态机 | 提供"手动重置本局"入口 |
| 显示器切换 | 窗口所在 output 变化 | 按窗口位置重选 `output_idx` |

## 10. 测试策略

| 层级 | 对象 | 方法 |
|---|---|---|
| L1 | 牌局引擎 | pytest 纯单测：规则、计分、主牌判定、记牌推理；覆盖 2/3 副 × 4/6 人组合 |
| L2 | 识别器 | 录制样本集回归：输出混淆矩阵与各类准确率，设最低阈值门禁 |
| L3 | 事件层 | 录制帧序列**离线回放**，断言产出的 PlayEvent 序列与墩边界正确 |
| L4 | 端到端 | 录一段真实牌局 → 回放 → 断言最终记牌结果与人工核对一致 |

**可测性前提**：帧序列可录制/回放，因此 L3/L4 不需要真实游戏在跑。

## 11. 校准与配置

- **一次性标定**：进入游戏后点击「标定」，截全屏并框选/确认各 ROI（4 个出牌区、手牌区、分数区、主牌指示区）
- **坐标表示**：ROI 存为**相对游戏窗口客户区左上角的归一化坐标**（`0.0~1.0`），不存绝对像素
- **运行时**：每次窗口移动/缩放后重新换算；尺寸与标定时不一致则按比例缩放 ROI，并对模板做多尺度匹配
- **配置文件**：JSON，含 ROI 定义、显示器序号、模板版本、阈值参数
- **DPI**：进程声明 Per-Monitor DPI Aware，避免逻辑/物理坐标错位

## 12. 风险与未决问题

| 风险 | 等级 | 说明与缓解 |
|---|---|---|
| **反作弊 / 封号** | **未知** | ⚠️ **未能核实**。读屏方案不改进程、不注入内存，属最低风险等级。但腾讯 ACE/TP 是否覆盖 QQ 游戏平台、记牌器是否被判定违规，本会话的 web 搜索工具因 API key 失效不可用，**未能查到可靠资料**。已确认的是此类工具（勇芳记牌器、我爱记牌器等）在中文互联网公开分发且持续更新。**投入前请自行评估风险，本设计不对此作保证。** |
| ROI 被遮挡 | 中 | Desktop Duplication 捕获**整个显示器**而非单窗口。若可切换到 Windows Graphics Capture（可抓被遮挡窗口）作为第二后端。 |
| 模板样本可得性 | 中 | 模板匹配需真实牌面图像。缓解：Phase 0 先交付**采样录制工具**，用 §4.5 的变化触发逻辑自动切片存盘，打两局即可攒齐样本，无需人工抓时机。 |
| 向日葵虚拟显示驱动 | 低 | 本机装有 `OrayIddDriver`（向日葵虚拟显示器）。实测 dxcam 在其存在时工作正常，但若通过远程桌面游玩，抓屏行为可能不同，需实测。 |
| 三副牌规则细节 | 中 | 手牌数/底牌张数需接入真实游戏后按实际 UI 校准确认（见 §7）。 |
| 模板匹配准确率上限 | 中 | 遮挡/重叠时掉分。缓解：可替换识别器接口，样本足够后升级 CNN；OCR 作为交叉校验。 |
| 皮肤/分辨率变更 | 低 | 自用场景下重复标定即可接受。 |

## 14. 实施分期

| 阶段 | 交付物 | 验证标准 |
|---|---|---|
| **Phase 0** | 采样录制工具 + 标定工具 | 能自动切出带时间戳的牌面样本切片，攒齐 54 类模板 |
| **Phase 1** | 采集层 + 识别器 + 事件层 | 离线回放：PlayEvent 序列与墩边界判定正确 |
| **Phase 2** | 牌局引擎（A）+ 悬浮窗 | 实时对局中剩余牌统计正确 |
